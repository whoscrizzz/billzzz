## Operational rules (hard constraints)

- **No deploy without explicit sign-off from the repo owner**, even though `deploy`/`deploy:safe` scripts exist and work.
- Never change DNS, routes, bindings, or production secrets without explicit OK.
- Never remove features or migrations without explicit OK.
- One change = one branch + PR (template at `.github/pull_request_template.md`); don't push experiments directly to `main`.
- A merged branch is deleted (local and remote) before starting the next one — don't let merged branches pile up.
- Secrets live in `.dev.vars` (local, gitignored) or `wrangler secret put` (prod) — never in `wrangler.jsonc` (non-secret vars only) or committed anywhere. Runtime secrets: `VAPID_PRIVATE_KEY`, `RESEND_API_KEY`.
- After editing `wrangler.jsonc` bindings, run `npm run cf-typegen` and check `worker/src/env.ts` still matches `Env` (`worker-configuration.d.ts` is generated and gitignored).
- Husky pre-commit runs `lint-staged` (prettier + oxlint) **and** `npm run typecheck`; commits with type errors fail locally.

## Architecture

Single Cloudflare Worker serving both the SPA and the API — **not** a two-worker setup:

```
Browser → billzzz.whoscrizzz.com/*
  /bills-api/*  → Worker API (worker/src/index.ts → routes.ts) — D1, auth, push, email
  /*            → ASSETS (dist/, Vite-built SPA, SPA fallback)
Cron (*/15 min) → push notifications + email digests + expired-auth-row purge
```

- **Rebrand note**: the app is user-facing "Billzzz" at `billzzz.whoscrizzz.com` (`wrangler.jsonc` `name: "billzzz-pwa"`, commit `a7e6381`), but internal identifiers deliberately kept the old `bills-` naming — npm package name (`package.json`), D1 database `bills-pwa-db`, IndexedDB `bills-pwa-u-<userId>`, and the `/bills-api` API prefix. Don't "fix" these to match the brand; they're stable identifiers, not user-visible strings. (A prior merge of the rebrand briefly corrupted this section into `/billzzz-api/` — it's `/bills-api/`, confirmed against `worker/src/constants.ts`.)
- **Frontend**: React 19 + Vite in `src/`, PWA via `vite-plugin-pwa` (manifest generated in `vite.config.ts` — there is no `public/manifest.json`).
- **Backend**: TypeScript in `worker/src/`, D1 binding `DB` (`bills-pwa-db`). API is entirely under `/bills-api/` (`worker/src/constants.ts`) — deliberately *not* `/api/`, which would hit the zone WAF on `whoscrizzz.com`. Routes have no `/v1` segment; the `API_VERSION` var in `wrangler.jsonc` is currently unused, and `APP_VERSION` only feeds client update checks (`src/services/update.ts` + `UpdatePrompt`).
- **Worker modules**: `index.ts` (fetch + `scheduled` + security headers), `routes.ts` (HTTP routing), `auth.ts`/`passkeys.ts`/`webauthn-config.ts`/`device-name.ts` (sessions + WebAuthn), `rate-limit.ts`, `subscriptions.ts` (CRUD, mark-paid, snooze, payment records), `capture.ts` (Fase 7b quick-capture via opaque `capture_token`, for Shortcuts/Siri), `notification-actions.ts` (Fase 6a signed action tokens for mark-paid/snooze/undo from the Service Worker, which has no access to the `localStorage` session token), `notes.ts`/`reminders.ts` (Notes+ CRUD, soft-delete), `reminder-notifications.ts` (reminder push cron), `settings.ts` (user settings, export/import, `/health`), `notifications.ts` + `notification-health.ts` (push cron), `email-digest.ts` (Resend), `calendar.ts` (tokenized `.ics` feeds), `due-dates.ts`/`due-dates-json.ts` (due-date math), `format-money.ts` (currency formatting shared by push/digest/`.ics`, see parallel-copy note below), `timezone.ts`.
- **Client data flow**: `useSubscriptions` does optimistic updates against IndexedDB (`src/lib/offline-db.ts`), which queues pending ops (`create`, `update`, `delete`, `mark-paid`, `snooze`, `restore-archived`) and replays them on reconnect via `src/lib/sync.ts`. The IndexedDB name is per-account (`bills-pwa-u-<userId>`); call `bindOfflineDbUser` on login/logout so accounts stay isolated.
- **Auth**: magic link (link or 6-digit short code) + optional passkeys; session token in `localStorage`, state in `AuthContext` (`src/contexts/AuthContext.tsx`). Special route `/auth/verify` (`src/pages/VerifyPage.tsx`) handles email links outside normal nav. `GET /bills-api/auth/verify` intentionally 405s — verification is POST-only so email scanners can't burn the token.
- **Auth flow is a staged wizard**, not separate screens: `LoginForm` owns `access → verify` (own 6-cell code input with its own keypad, resend), then `PostLoginPasskeyOffer` / `PostLoginPushOffer` / `PostLoginOnboarding` continue the same visual flow. `AuthStepIndicator` (3 bars) is shared across all of them, and each offer is gated by a `sessionStorage` flag with `mark…OfferPending` / `shouldOffer…` / `clear…OfferPending` helpers exported from its own component file. First-run onboarding seeds bills from `src/lib/quick-templates.ts` and can import from JSON or Reminders. Auth screens read their own `--auth-*` CSS tokens — no other selector uses them.
- **Revoking access is `users.disabled`** (migration `0017`, `npm run revoke -- <email>`, `--undo` to restore) — never a `DELETE` of the `users` row, which is destructive and blocked by five FK children. The flag is checked in *seven* places — every path that resolves a user without `getSessionUserId`, since those are built to work without a session and so survive any credential change: `findUserIdByEmail` (login), `getSessionUserId` (it JOINs `users` for exactly this reason — don't "simplify" that join away), `serveCalendarFeed`, `captureExpense`, `verifyActionToken` + `resolveGroupActionAuth` (push buttons, 14-day window, and they *write*), `getUserEmail` (passkey login, which mints a session without touching the email path), and the push/email cron queries. Any new identity-resolving path needs the check plus a case in `scripts/test-user-disabled.mjs`.
- **Registration is invite-only** — no auth path creates a `users` row; accounts come from `npm run invite -- <email>` (`:remote` for prod). An unknown address gets a response identical to a real send, so don't "fix" it into a 404. **The API never returns `verifyUrl`/`shortCode` in a response body, in any environment** — missing email config returns 503, and local dev pulls the pending link from D1 via `npm run dev:link -- <email>`. Don't re-add a dev-only echo: `wrangler dev` rewrites `request.url` *and* the `Host` header to the `custom_domain` in `wrangler.jsonc`, so there is no host-based way to tell dev from prod inside the Worker (see `SECURITY.md`).
- **Navigation**: in-app tabs (`home | add | calendar | settings`) kept in sync with the `?p=` query param via `src/lib/nav-route.ts`, not a router library. Heavy panels are `React.lazy` imports in `App.tsx`.
- **Responsive UI**: single React tree for browser tab and installed PWA, breakpoint at 768px — desktop gets a sidebar (collapsible to an icon rail) and flat/category list toggle; mobile gets bottom nav and FAB quick-add. **Cards have no swipe gesture** — it was removed as redundant with the check button and `SnoozeMenu`; snoozing is a long-press (`LONG_PRESS_MS` in `SubscriptionCard.tsx`) wired through Pointer Events, not touch-only, so mouse users on desktop keep the action. Don't reintroduce swipe handlers here. The topbar avatar doubles as the online/offline indicator. `FloatingCalculator` lives in `AppLayout` and persists across tabs; its open state is lifted into `CalculatorContext` so topbar, Settings, and the register sheet all drive the same panel — open it with `useCalculator().openCalculator({ initialValue, onUseAsAmount, onUseAsBudget })` rather than mounting another instance.
- **Theming**: `src/lib/theme.ts` is the single source — `light | dark | auto` persisted in `localStorage`, resolved to `document.documentElement.dataset.theme` plus the `theme-color`/`color-scheme` meta tags. `useTheme()` is called once in `App.tsx`; `auto` follows `prefers-color-scheme` live. Styling goes through the CSS custom properties at the top of `src/App.css` (`--bg`, `--card`, `--text`, `--accent`, …) — every token has a `[data-theme='dark']` counterpart there, so hard-coded colors in components silently break dark mode.
- **Category color is `categoryColor()` in `src/lib/categories.ts` — the only way to paint a category.** It resolves a fixed hue table from the design handoff at a fixed `62% 52%`, falls back to a hash for free-text categories, and returns a neutral grey for `Otros`/`Sin categoría`/empty (those are the *absence* of a category, not one more). It replaced three identical hash functions that each hardcoded their own saturation (`48% 44%`, `55% 52%`, `52% 48%`) — that drift is exactly what centralising this prevents, so build the CSS color here, never `hsl(...)` at the call site. `computeCategorySlices` deliberately returns no `hue` field.
- **`RecurrenceSheet` has 8 frequency chips.** `Quincenal` writes fixed `due_days` (grid, multi-select, "Quincenas (1 y 15)" preset); `Personalizado` keeps the rolling `frequency: 'interval'` editor (`Cada N` + unit) — removing it would make "cada 3 meses" unexpressible and regress the hydration fix in PR #94. `MultiDateChips` and `WeekdayPills` (multi-date list, weekly day picker) are used exclusively by `RecurrenceSheet` — don't delete them as apparently-dead code.
- **UI prefs** (list layout, sort mode, last login email, sidebar collapsed, round cents) go through `src/lib/ui-prefs.ts`; add new `localStorage` keys there rather than inline. Money is always rendered via `formatMoney`/`formatMoneyCompact` (`src/lib/format-money.ts`), which reads the round-cents pref — don't call `Intl.NumberFormat` directly in components.
- **Spending insights** (`src/lib/spending-stats.ts`, surfaced by `SpendingOverview`/`TodayPanel`) are pure functions over the subscription list: `monthlyEquivalent` normalizes any recurrence to a per-month amount (weekly ×52/12, yearly ÷12, interval ×30.44/days), and on top of it sit `computeBudgetOutlook` (vs `users.budget_limit`), `computeTotalsByCurrency`, `computeCategoryTotals`, `computePriceIncreases`, `computeMonthComparison`, `computeMonthlyTotal`, `computeCalendarMonth`, `computeCategorySlices`. Totals are never summed across currencies — group by currency first (the category accordion on Inicio sorts groups by their largest single-currency total for the same reason). Covered by `scripts/test-spending-stats.mjs`.

## Data model (D1, `migrations/`)

Forward-only numbered SQL files (`0001`–`0019`), applied with the `db:migrate:*` scripts. Tables: `users`, `sessions`, `magic_links`, `subscriptions`, `payment_records`, `push_subscriptions`, `notification_log`, `notification_attempts`, `notification_actions`, `passkey_credentials`, `webauthn_challenges`, `auth_rate_limits`, `notes`, `reminders`. Schema changes are additive `ALTER TABLE … ADD COLUMN` with NULL defaults so existing rows keep working; never rewrite an applied migration — the one exception is a `NOT NULL` that has to be dropped, which SQLite can't do in place and which `0005`/`0016` handle by rebuilding the table (create `_new`, copy, `DROP`, `RENAME`, recreate indexes).

- `subscriptions.due_dates` is a JSON array of `{ date, amount? }` entries (per-date optional override); parse/serialize only through `due-dates-json.ts`, and read the effective amount with `currentDueAmount`. Legacy rows may still hold a plain `string[]` or only the older `due_date` column — `parseDueDates` normalizes all three, so never `JSON.parse` the column by hand.
- **Recurrence has four layers, resolved in a fixed precedence** (`due-dates.ts`, mirrored in `spending-stats.ts`): explicit `due_dates` list → perpetual `due_days` (JSON array of month days, e.g. `[1, 15]` for quincenal) → `frequency: 'interval'` with `interval_count`/`interval_unit` (`day | week | month`) → plain `frequency` (`monthly | weekly | yearly | once`) anchored on `due_day`/`due_date`. `due_days`, `interval_count`, and `interval_unit` arrived in migration `0012` and are NULL on every pre-existing row, so all four paths stay live — adding a branch means updating `daysUntilNextDue`, `describeRecurrence`, `advanceDueDateAfterPayment`, `monthlyEquivalent`, and `dueDaysInMonth` together. `RecurrenceSheet` is the only UI that writes these fields.
- `payment_records` is the payment history behind `/bills-api/payments` (list, delete one, clear all); mark-paid writes it and un-marking pops the last record. Since `0016`, `subscription_id` is **nullable**: a NULL row is a loose expense captured without a bill behind it (Shortcuts/Siri, shared text — see `captureExpense`), and it carries its own `name`/`category`, which for a normal subscription payment stay NULL and are read from the subscription via JOIN. Any query over this table has to tolerate the NULL side of that join.
- `notification_log` stores the dedup key; `notification_attempts` stores per-attempt outcomes (`sent`/`failed`/`expired`) feeding `/bills-api/notifications/health`. `notification_actions` (`0015`) is a *different* table with the same `subId:nextDue:daysLeft` key — it records mark-paid/snooze taken **from** a notification so the action can be undone, and unlike `notification_log` its row is not released when a delivery fails.
- `subscriptions` has two distinct soft-delete columns: `trashed_at` (`0013`, user-facing trash, purged automatically at 30 days) and the older `deleted_at`, which stays exclusive to the automatic archive when a `once`/finished subscription is paid (`markSubscriptionPaid`). They are not interchangeable.
- **Notes+** (`notes`, `reminders`, migration `0018`) is a ported standalone app now living as a panel (`NotesHub.tsx`). `notes.category` is free text painted with `categoryColor()`, not a fixed enum. `reminders.notified_at` is the cron's dedup claim — unlike `notification_log`'s composite `notification_key`, a reminder isn't recurring, so the claim is a direct `UPDATE ... WHERE notified_at IS NULL` on the row itself (`sendDueReminders` in `reminder-notifications.ts`). Both tables got `trashed_at` in migration `0019`, same pattern and 30-day auto-purge as `subscriptions` — `deleteNote`/`deleteReminder` are soft-deletes, `list*`/`update*` filter `trashed_at IS NULL`, and the reminder cron query additionally filters it so a trashed reminder never triggers a push.

## Conventions and gotchas

- **Worker and SPA are separate bundles with no shared imports.** `due-dates.ts`, `due-dates-json.ts`, `format-money.ts`, and the timezone allowlist exist as parallel copies in `worker/src/` and `src/lib/` (`notify-timezone.ts`). Change one, change the other — the copies' comments say so, and drift silently splits client and server math. The copies are deliberately *not* byte-identical: the client types against `Subscription` (`src/types/subscription.ts`), computes "today" in the browser's local zone (`local-date.ts`), and its `formatMoney` respects the "Redondear centavos" UI pref; the worker types against `SubscriptionRow` (`worker/src/env.ts`), resolves the day through `getDateInTimeZone` in the user's stored timezone, and its `formatMoney` wraps `Intl.NumberFormat` in a try/catch because the currency code comes from D1 unvalidated. Port the logic, not the date/UI plumbing. `scripts/test-worker-client-parity.mjs` guards this mechanically for `due-dates-json.ts` and the timezone allowlist — it diffs every exported pure function between both copies and fails if a new export has no case, so a new parallel-copy pair should get the same treatment rather than relying on the comment alone.
- **Notification timing**: `notify_hour` is a wall-clock hour in the *owning user's* timezone (`users.timezone`, default `America/Mexico_City`, picked from the allowlist in `worker/src/timezone.ts`). The cron fires every 15 minutes; `shouldNotifyNow` gates on the `[notify_hour, notify_hour+1)` window, upcoming within `notify_days_before`, and overdue up to 7 days.
- **Dedup is a claim, not a check.** `sendDueNotifications` INSERTs the `subId:nextDue:daysLeft` key into `notification_log` *before* sending (UNIQUE constraint makes it atomic across overlapping ticks) and releases the claim if there are no endpoints or every delivery failed. Keep that ordering when touching push code. Same pattern in `rate-limit.ts`: one UPSERT with `RETURNING`, never SELECT-then-UPDATE. `createSubscription`/`createNote` apply the same principle to the row's own id: the client generates it (`crypto.randomUUID()`) and sends it in the create payload, the server uses it as the PRIMARY KEY, and a retried create (offline reconnect firing twice, a network retry) hits the constraint and gets back the existing row (200) instead of a duplicate. `sync.ts`/`notes-sync.ts` rely on this — the id never changes between local and remote, so there's no id-remapping step in their queue replay.
- **`sync.ts` and `notes-sync.ts` are a near-identical pair** (offline queue replay for subscriptions vs. notes — same `inFlight` reconnect guard, same 4xx-discard/5xx-retry logic in the catch), not a shared abstraction. If you fix a bug in one (e.g. another reconnect race), port the fix to the other by hand — nothing enforces they stay in sync. Deliberately not unified: touching the subscriptions sync engine (real money, one prior production bug there — commit `85daa66`) to DRY up the notes copy is a worse trade than the duplication itself. Revisit only if a third queue shows up (rule of three) or the reconnect race resurfaces in one of the two.
- **Every response passes through `withSecurityHeaders`** in `worker/src/index.ts`, including static assets. The CSP is strict same-origin (`script-src 'self'`, `connect-src 'self'`) — any external font, script, image host, or analytics endpoint requires editing that header, and there is currently no reason to.
- **Service worker gate**: `npm run build` runs `scripts/check-sw.mjs`, which fails if `dist/sw.js` lost its `/bills-api/` runtime route or leaked the literal `API_PREFIX` identifier. Workbox precaches the app shell and marks `/bills-api/*` `NetworkOnly` (no API responses are cached); push handling lives in `public/sw-push.js`, pulled in via `importScripts`. `registerType` is `'prompt'` — updates surface through `UpdatePrompt`, they don't auto-apply.
- **Language**: user-facing strings, API error messages, and commit messages are Spanish (`es-MX`); identifiers, code comments, and docs headings are English. Match the surrounding file.
- **Formatting/lint**: prettier (single quotes, 100 cols, semicolons, es5 trailing commas) and oxlint with `typescript/no-floating-promises` and `react/rules-of-hooks` as errors — floating promises in async handlers will fail `validate`.
- **CI**: `.github/workflows/ci.yml` runs `npm audit --audit-level=high --omit=dev` (production deps only) plus `validate` and `build` on every PR. `deploy.yml` deploys on push to `main` when the Cloudflare secrets are present, and skips with a warning when they aren't.

## Local dev ports

Fixed defaults: Worker `8787`, Vite `5173` — both `127.0.0.1` only (no tunnels, no Zero Trust, no exposing dev by public IP/DDNS). Vite's dev server binds `host: '127.0.0.1'` explicitly (`vite.config.ts`) rather than letting Vite resolve `localhost` via DNS, which on some Macs returns only the IPv6 `::1` and leaves the port unreachable over IPv4. **Always open `http://localhost:PORT` in the browser, never the raw `127.0.0.1` URL** — WebAuthn rejects an IP address as `rpId`, so passkeys silently break if you dev against the IP. To run multiple worktrees/checkouts in parallel, override via `VITE_PORT`/`VITE_API_PORT` in a gitignored `.env.local` per checkout — both `vite.config.ts` and `scripts/dev-api.mjs` read it through Vite's `loadEnv`, so the two stay consistent. Check other worktrees' `.env.local` first to avoid collisions (`git worktree list`).
